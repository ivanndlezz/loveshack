# Plan: Fix Random Reloads + Visual Blipping in Yacht Pricing Screen (v3)

**Plan ID:** 1779733309152-eager-knight  
**Created:** 2026-05-25  
**Status:** Ready for implementation (after user review)  
**Scope:** `v3/js/screens/yacht-pricing.js` + minimal supporting changes in `v3/css/screens/yacht-pricing.css` (if needed for layout stability)  
**Priority:** High (user-reported production-like instability: random full-page reloads + "blipping")

## 1. Problem Statement
The Yacht Pricing Comparator screen (`#/yacht-pricing`) exhibits two related defects:
- **Random full-page reloads** — especially when the user presses Enter while focused in any of the many `<input type="number">` fields (commission inputs + dynamic hourly slots in the edit/import sheets).
- **Visual "blipping" / layout thrashing** — frequent flashes, reflows, and jarring re-renders on routine interactions (changing cohort, stepping values, switching tabs, opening sheets, CRUD actions).

The reload logger (added earlier in `app.js`) surfaces `beforeunload` and occasional `location.reload` traces when these events occur.

User feedback:
- Blipping existed *before* the internal tab-bar was moved into the header → rule out the current header structure as primary cause.
- Strong agreement that form-submit-on-Enter and heavy DOM replacement are the root causes.

## 2. Root Cause Analysis (Research Summary)
Research performed via direct reads, targeted greps, and an explore agent task on the full 1123-line file + related router/CSS:

### Primary Causes (Ranked by Likelihood + Impact)

1. **Form submit on Enter in number inputs (highest confidence for reloads)**
   - Two persistent `<form>` elements are always in the DOM (even when sheets are closed):
     - `#source-form` (line 202)
     - `#import-form` (line 258)
   - Both have `onsubmit="...handleFormSubmit(event)"` + `event.preventDefault()` as first statement.
   - `openFormModal()` dynamically injects **21+ number inputs** (3 per cohort × 7 cohorts) directly inside `#form-hourly-slots-container` which lives inside `#source-form` (lines 792-801).
   - Commission number inputs (`#form-commission-input`, `#import-commission-input`) + other fields are also form descendants.
   - No `type="button"` on the vast majority of `<button>` elements (only explicit Cancel/Submit buttons have it). No `novalidate`. No keydown Enter blockers on inputs.
   - Inline `onsubmit` + fragile event object passing in a large template string is timing-sensitive when combined with sheet open/close + `void offsetWidth` forced reflows.

2. **Heavy full/partial innerHTML replacement on nearly every user action (primary blipping cause)**
   - `render()` (line 30): always calls `destroy()` then `container.innerHTML =` (massive ~150-line template).
   - `destroy()` (line 409): `container.innerHTML = ''`.
   - `renderRatesList()` (line 646): clears + rebuilds entire grid on every call.
   - `calculateAll()` + `renderComparisonCard()`: repeated `innerHTML =` on comparison cards and diff banner.
   - `updateComparisonSelectors()`: clears and repopulates selects.
   - Triggered constantly by `setCohort`, `stepInput`, source selects, tab switches, catalogue-cohort onchange, every CRUD operation (which then call `update*` + `calculateAll`).
   - Combined with many CSS transitions + absolute/fixed positioning on sheets + forced reflows (`void sheet.offsetWidth`).

3. **Mixed event handling patterns + lack of cleanup (amplifies both symptoms)**
   - 20+ inline `onclick`/`oninput`/`onchange` in the template string.
   - A few `addEventListener` calls in `_wireStaticListeners` (re-run on every render).
   - `renderRatesList` does `container.onclick = ...` (assignment, not add) on every rebuild.
   - Almost no `removeEventListener` in `destroy()` (only timer + HTML wipe).
   - Global exposure via `window.YachtPricingScreen` for all inline handlers.

4. **Missing method + other latent bugs**
   - `btnCopy` listener (line 398) references `this.handleCopyReport()` — the method is never defined on the object (only a stub existed in early skeleton). Will throw on click.
   - Data constants (`DEFAULT_PRICING_DATA` etc.) defined after the object literal (harmless at runtime but poor hygiene).

5. **Secondary contributors**
   - No isolation of form controls (e.g., `form` attribute, explicit `type=button` on generated content).
   - Router calls `route()` in several places (data sync, imports, logger noise) — any accidental navigation while the screen is mounted amplifies the heavy render cost.
   - Large template literals + repeated string building inside loops.

The combination of (1) + (2) + (3) perfectly explains the symptoms: Enter in any focused number field → form submit → reload; any cohort/step/tab/CRUD action → mass DOM replacement → visible blip.

## 3. Goals & Non-Goals

**Goals**
- Eliminate accidental full-page reloads triggered by Enter in number inputs inside the Yacht Pricing forms.
- Dramatically reduce or eliminate visual blipping on normal interactions.
- Keep 100% of existing functionality and behavior (simulator, CRUD, import, commission number+slider sync, persistence, etc.).
- Make the code more maintainable and less fragile for future changes.
- Preserve the "port fidelity" style (self-contained screen) while applying targeted v3 best practices.

**Non-Goals**
- Full architectural rewrite of the screen into a modern component system (unless user explicitly requests later).
- Changes to the original data model or localStorage key.
- Removing the global `window.YachtPricingScreen` exposure (required by the many inline onclick handlers; can be cleaned in a follow-up if desired).
- Performance work on very large catalogs (not a current pain point).

## 4. Proposed Solution (Phased, Incremental, Low-Risk)

### Phase 0 – Diagnostics & Baseline (1-2 hours)
- Ensure the reload logger in `app.js` is active.
- Reproduce the exact scenarios (Enter in commission input, Enter in a slot input while sheet open, cohort change, etc.) and capture logger output + screenshots of blips.
- Confirm `handleCopyReport` throw (click the copy report button).

### Phase 1 – Stop the Reloads (Highest ROI, ~2-3 hours)
**Minimal, targeted changes only in yacht-pricing.js**

1.1 Add `type="button"` to **every** non-submit `<button>` in the static template and in all dynamic HTML strings (`renderRatesList`, rate cards, delete confirms, etc.).

1.2 Add robust Enter-key blocking for all number/text inputs that live inside the two forms:
   - In `_wireStaticListeners` (and after dynamic injection in `openFormModal` / import sheet open).
   - Use capture-phase keydown listener on the forms or a document-level guard scoped to `#yacht-pricing-root`.
   - Also add `novalidate` on both forms.

1.3 Make the two submit handlers even more defensive (early return if the event target is inside a non-submit context — belt + suspenders).

1.4 Fix the missing `handleCopyReport` method (port the original implementation or stub it safely).

**Verification:** No more reloads when pressing Enter in any input while the screen is active. Logger should show zero `beforeunload` traces from normal typing.

### Phase 2 – Reduce Blipping / Thrashing (Medium effort, high user-visible win) (~4-6 hours)

2.1 Introduce lightweight "partial update" helpers instead of blanket `innerHTML = ''`:
   - `updateComparisonCards(resA, resB)` — only touch the two card containers + diff banner.
   - `updateSelectors()` — only repopulate the two source selects (already mostly does this, but make it the only path).
   - `updateRatesList(cohortKey?)` — use a document fragment or targeted replace for the rates grid instead of full clear + rebuild on every call. At minimum, avoid rebuilding the header select if the cohort didn't change.

2.2 Add a cheap "already mounted" guard at the top of `render()`:
   ```js
   if (this.container === container && container.querySelector('#yacht-pricing-root')) {
     // just refresh volatile parts
     this.initApp(); // or a lighter refreshData()
     return;
   }
   ```
   This prevents full re-inject when the router re-calls the screen for the same hash (common with loggers, syncs, etc.).

2.3 Move any forced reflow (`void offsetWidth`) behind requestAnimationFrame or only when the sheet is actually transitioning.

2.4 Extract the two big forms into static methods that return the HTML once where practical, and implement dedicated small updater helpers for the most expensive areas (comparison cards, rates list rows, selectors).

**Decision:** User selected the "Thorough" version of Phase 2.

**Verification:** Blipping is either gone or dramatically reduced on cohort changes, stepping, tab switches, and CRUD. Measured subjectively + via performance tab "long tasks".

### Phase 3 – Event Hygiene & Destroy Hardening (2 hours)
- Replace as many inline `onclick` as practical with delegated listeners attached once in `_wireStaticListeners` (or a new `setupDelegatedHandlers`).
- Ensure `destroy()` removes the `container.onclick` delegate and any other listeners it attached.
- Add a small "mounted" flag to prevent double-wiring.

### Phase 4 – Polish, Docs, and Follow-ups (optional, 1-2 hours)
- Clean up the data constants placement (move before the object).
- Add a comment block at the top of the file documenting the known fragile patterns and the hardening that was applied.
- If user wants: propose a follow-up ticket to migrate away from global `window.YachtPricingScreen` + inline handlers (bigger refactor).

## 7. Risks & Mitigations
- **Risk:** Over-aggressive Enter blocking breaks legitimate form submission via keyboard.  
  **Mitigation:** Only block when target is an input inside the pricing forms; still allow the real submit buttons to work.
- **Risk:** Partial-update refactor introduces subtle bugs in comparison cards or rates list.  
  **Mitigation:** Keep the old full-rebuild paths behind a dev flag or as fallback during development; test exhaustively.
- **Risk:** Scope creep into full rewrite.  
  **Mitigation:** Strict "targeted hardening only" rule for Phases 1-3.
- **Risk:** The many inline handlers make some changes tedious.  
  **Mitigation:** Prioritize the reload fix (Phase 1) first — it gives immediate user relief even if blipping is only partially improved.
